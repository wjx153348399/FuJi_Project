# 实时上传第一版修改计划

本文档用于确认“自动上传小工具”第一版实时上传改造范围。确认无误后，再按本文档进行代码修改。

## 1. 改造目标

在保留现有文件识别规则、上传接口、工站目录规则和历史去重规则的前提下，将现有“定时扫描上传”升级为“监听目录变化后实时上传”。

第一版需要满足：

- 监听目录中文件新增、修改、移动事件。
- 监听到符合现有上传规则的文件后，直接触发上传。
- 不再依赖每天定时任务作为主上传触发方式。
- 上传过程、上传结果、错误信息可以在 Web 页面查看。
- 部署到服务器后，其他用户可以通过浏览器访问工具页面。
- 服务器上 Web 服务和监听上传服务先采用双进程部署。

## 2. 第一版保持不变的规则

第一版只改变触发方式，不改变业务规则。

必须保持不变：

- 文件扩展名规则继续使用 `scan.extensions`。
- 临时文件排除规则继续使用 `scan.exclude_prefixes`。
- 排除目录规则继续使用 `scan.exclude_dirs`。
- 工站目录和 `flow` 规则继续使用现有 `scan.targets` 或数据库配置。
- 上传接口地址、请求字段、超时、重试规则继续使用现有 `upload` 配置。
- 历史成功上传去重规则继续使用现有日志和指纹文件。
- `upload.day_offset` 日期窗口规则第一版继续遵守。

继续遵守 `upload.day_offset` 的原因：

- 避免实时监听后扩大上传范围。
- 避免旧文件或测试文件被修改后误上传。
- 保证第一版只改变“什么时候触发上传”，不改变“哪些文件可以上传”。

## 3. 第一版不做的内容

以下内容第一版暂不实现，避免一次改造范围过大：

- 不做日志入库。
- 不新增日志字段到现有工站配置表。
- 不做用户登录和权限控制。
- 不做企业微信、邮件、短信等告警。
- 不做复杂报表统计。
- 不做手动补传功能。
- 不做 Windows 服务化封装。
- 不合并 Web 服务和监听服务为同一个进程。

说明：

- 日志第一版继续写 JSONL 文件。
- Web 页面第一版通过读取日志文件展示运行日志和错误日志。
- 后续如果日志查询量大或需要长期审计，再新增独立日志表。

## 4. 推荐模块调整

当前核心模块：

- `zk_impedance_upload/runner.py`：现有扫描上传主流程。
- `zk_impedance_upload/watcher.py`：现有监听模块，目前只记录变化，不触发上传。
- `zk_impedance_upload/log_store.py`：现有日志读写模块。
- `station_config_web/app.py`：现有 Web 配置页面。

建议调整后的职责：

```text
zk_impedance_upload/
  runner.py              保留手动上传入口和兼容旧流程
  upload_pipeline.py     新增，沉淀可复用的上传处理流程
  realtime_uploader.py   新增，负责编排监听事件、稳定性检查、队列、防重复、触发上传
  watcher.py             修改，负责目录监听和事件产生
  log_store.py           修改，增加日志读取能力，供 Web 页面展示
  config.py              修改，增加实时监听必要配置

station_config_web/
  app.py                 修改，增加 dashboard、logs 和日志 API
  templates/
    dashboard.html       新增，运行状态首页
    logs.html            新增，日志详情页
```

职责边界：

- `watcher.py` 只负责发现变化。
- `realtime_uploader.py` 负责判断是否可上传、等待文件稳定、排队和触发上传。
- `upload_pipeline.py` 负责复用现有解析、去重、上传、写日志逻辑。
- `log_store.py` 负责统一写入和读取日志。
- Web 页面只负责展示状态、日志和配置页面。

## 5. 实时监听实现计划

### 5.1 引入监听库

在 `requirements.txt` 增加：

```text
watchdog>=4.0.0
```

监听事件包括：

- 文件新增
- 文件修改
- 文件移动或重命名

目录删除和文件删除只记录日志，不触发上传。

### 5.2 监听目录来源

监听目录继续来自现有配置：

1. 优先读取启用状态的 `scan.targets`。
2. 没有 `scan.targets` 时读取 `scan.target_dirs`。
3. 两者都没有时监听 `share.root`。

如果启用了数据库工站目录配置，则继续通过现有数据库配置读取有效目录。

### 5.3 文件事件处理流程

监听到文件事件后，按以下流程处理：

```text
文件事件
  -> 判断是否是文件
  -> 判断扩展名是否符合 scan.extensions
  -> 判断是否命中 scan.exclude_prefixes
  -> 判断是否位于 scan.exclude_dirs 下
  -> 防抖合并短时间重复事件
  -> 等待文件写入稳定
  -> 判断是否符合现有日期窗口规则
  -> 解析文件信息
  -> 历史去重
  -> 调用上传接口
  -> 写入上传日志和运行日志
```

### 5.4 文件稳定性检查

监听到文件变化后，不能立即上传。需要确认文件写入完成。

建议规则：

- 每隔 `stable_check_seconds` 检查一次文件大小和修改时间。
- 连续 `stable_check_attempts` 次没有变化，才认为文件稳定。
- 如果文件被占用或读取失败，记录日志并稍后重试或跳过。

建议新增配置：

```json
{
  "watch": {
    "enabled": true,
    "debounce_seconds": 5,
    "stable_check_seconds": 2,
    "stable_check_attempts": 3,
    "queue_max_workers": 1
  }
}
```

### 5.5 防重复处理

一个文件保存时可能触发多次 `modified` 事件。

第一版需要做到：

- 同一路径短时间内重复事件只处理一次。
- 同一文件正在上传时，不重复加入队列。
- 上传成功后继续使用现有历史记录避免重复上传。

默认采用串行上传：

```text
queue_max_workers = 1
```

原因：

- 减少共享盘读取冲突。
- 减少上传接口并发风险。
- 便于第一版排查问题。

## 6. 上传流程复用计划

当前 `runner.py` 是扫描目录后批量上传。实时上传需要支持单文件事件触发。

建议抽出公共流程：

```text
run_upload_task()
  保留，兼容手动执行和旧任务

process_upload_candidates()
  新增，处理候选文件列表

process_realtime_file()
  新增，处理监听到的单个文件
```

要求：

- 手动上传和实时上传共用解析、去重、上传、日志写入逻辑。
- 不复制一份新的上传逻辑。
- 不绕过现有历史成功记录。
- 不绕过现有 dry-run 配置。

## 7. 日志展示计划

### 7.1 日志存储方式

第一版不新增数据库字段，也不新增日志表。

继续使用现有文件日志：

- `upload_log_YYYY-MM-DD.jsonl`
- `watch_log_YYYY-MM-DD.jsonl`
- `summary_YYYY-MM-DD_HH-MM-SS.json`
- `uploaded_file_fingerprints.json`
- `uploaded_business_keys.json`

原因：

- 现有项目已经具备文件日志能力。
- 第一版改动小、风险低。
- 不影响现有数据库结构。
- Web 页面读取 JSONL 即可满足日志上屏需求。

### 7.2 日志内容要求

界面中至少展示：

- 时间
- 日志类型
- 文件名
- 文件完整路径
- `flow`
- 处理状态
- 上传结果
- HTTP 状态码
- 错误原因
- 重试次数

需要重点展示的错误：

- 上传接口失败。
- 上传接口超时。
- 上传返回异常状态。
- 文件解析失败。
- 文件被占用或未写入完成。
- 共享盘访问失败。
- 监听目录不存在。
- 日志目录不可写。
- 数据库读取工站目录失败。
- 配置读取失败。

### 7.3 日志页面

新增页面：

```text
/dashboard        工具首页，展示运行状态和最新日志
/logs             日志详情页
/station-config   原工站目录配置页，保留
```

根路径调整：

```text
/ -> /dashboard
```

`/dashboard` 显示：

- 监听服务状态。
- 最近监听事件。
- 最近上传结果。
- 今日成功数量。
- 今日失败数量。
- 今日跳过数量。
- 最新错误日志。

`/logs` 支持：

- 按日志类型筛选。
- 按成功、失败、跳过筛选。
- 按文件名、路径、`flow`、错误内容搜索。
- 默认展示最近 200 条。

### 7.4 日志 API

新增接口：

```text
GET /api/status
GET /api/logs?type=all&level=all&limit=200
GET /api/logs/latest
```

第一版前端可采用 2 秒轮询刷新日志。后续如有需要，再升级为 SSE 实时推送。

## 8. 服务器部署计划

第一版采用双进程部署：

```text
进程 1：Web 服务
uvicorn station_config_web.app:app --host 0.0.0.0 --port 8000

进程 2：实时监听上传服务
python run_watcher.py --config D:\PythonProject\ZK\config.json
```

双进程原因：

- Web 页面和监听上传职责分离。
- Web 重启不必影响监听上传的代码结构。
- 监听上传异常时更容易单独排查。
- 上传接口慢或共享盘卡顿时，不拖慢页面响应。
- 第一版上线风险更低。

服务器访问地址：

```text
http://服务器IP:8000/
```

上线前需要确认：

- 服务器账号可以访问共享盘。
- 服务器账号可以写入日志目录。
- 服务器可以访问上传接口。
- 如果启用数据库配置，服务器可以访问 SQL Server。
- Web 服务端口已对使用人员开放。
- 监听进程可以保持常驻运行。

## 9. 代码清理计划

确认第一版需求后，可以在不影响功能的前提下清理冗余代码。

### 9.1 可以清理或降级的内容

如果实时上传成为主流程，以下内容可以评估清理：

- `watcher.py` 中只用于“每日监听汇总”的逻辑，如果 Web 日志页面已经替代该用途，可以降级为兼容功能。
- README 和部署文档中“每天定时任务是主上传方式”的描述需要更新。
- 与旧定时上传主流程强绑定的说明和示例命令需要调整为“手动补充执行”或“兼容入口”。
- `watch.notice_mode=log_and_daily_summary` 如果后续没有实际使用，可以保留配置但不作为第一版主路径。

### 9.2 必须保留的内容

以下内容不能清理：

- `run_upload.py` 手动上传入口。
- `run_watcher.py` 监听服务入口。
- `runner.py` 中现有上传主流程，直到公共上传流程抽取完成并测试通过。
- 历史上传记录文件读取和写入逻辑。
- `summary_*.json` 写入逻辑，除非新页面完全替代且测试覆盖充分。
- `watch_log_*.jsonl` 写入逻辑。
- 现有测试覆盖的配置、扫描、解析、去重、上传模块。

保留 `run_upload.py` 的原因：

- 可用于上线前手动验证。
- 可作为实时监听漏事件时的兜底补扫。
- 可用于故障排查。

### 9.3 清理原则

代码清理必须遵守：

- 先补测试，再清理。
- 不改变现有上传结果。
- 不改变现有日志文件格式，除非同步兼容读取。
- 不删除仍被文档、入口脚本或测试引用的函数。
- 不一次性做大规模重构。
- 清理前后运行完整测试。

建议清理顺序：

1. 抽出公共上传流程，减少 `runner.py` 和实时上传之间的重复。
2. 替换旧监听中的轮询上传相关描述。
3. 保留旧入口，更新其定位为“手动执行 / 兼容 / 补扫”。
4. 删除已经没有引用的私有函数。
5. 更新 README 和部署文档。

## 10. 测试计划

### 10.1 单元测试

新增或修改：

```text
tests/test_realtime_uploader.py
tests/test_watcher.py
tests/test_log_store.py
tests/test_station_config_web_app.py
tests/test_runner.py
```

覆盖：

- 非 Excel 文件不上传。
- `~$` 临时文件不上传。
- 排除目录中的文件不上传。
- 符合规则的文件进入上传流程。
- 同一文件多次事件只上传一次。
- 文件未稳定时不上传。
- 上传成功写入成功日志。
- 上传失败写入错误日志。
- Web API 能读取上传日志和监听日志。
- `/` 正确跳转到 `/dashboard`。

### 10.2 手工验收

上线前手工验收：

1. 启动 Web 服务。
2. 访问 `/dashboard`。
3. 启动监听上传服务。
4. 放入不符合规则的文件，确认不上传。
5. 放入符合现有规则的 Excel 文件。
6. 确认界面出现监听日志。
7. 确认文件稳定后自动上传。
8. 确认上传成功显示在界面。
9. 模拟上传接口失败，确认错误显示在界面。
10. 多次修改同一文件，确认不会重复上传。
11. 重启服务后，确认历史已上传文件不会重复上传。

## 11. 实施顺序

建议按以下顺序修改：

1. 新增或抽取公共上传流程。
2. 引入 `watchdog` 并改造监听模块。
3. 增加文件稳定性检测。
4. 增加实时上传队列和防重复处理。
5. 接入现有上传流程。
6. 扩展日志写入和读取能力。
7. 增加 `/dashboard`、`/logs` 和日志 API。
8. 调整 `/` 跳转到 `/dashboard`。
9. 更新测试。
10. 更新部署文档。
11. 在测试通过后清理无用代码。

## 12. 第一版验收标准

确认通过以下条件后，第一版可上线：

- [ ] 放入符合现有规则的文件后，可以自动上传。
- [ ] 不符合现有规则的文件不会上传。
- [ ] 上传不再依赖每天定时任务触发。
- [ ] 文件还在写入时不会提前上传。
- [ ] 同一文件不会因为多次事件重复上传。
- [ ] 上传成功日志可以在界面看到。
- [ ] 上传失败原因可以在界面看到。
- [ ] 监听目录异常可以在界面看到。
- [ ] `/` 可以进入工具首页。
- [ ] `/station-config` 原配置功能保留。
- [ ] 服务器上其他用户可以通过浏览器访问。
- [ ] Web 服务和监听上传服务可以分别启动、停止、排查。
- [ ] 自动化测试通过。
